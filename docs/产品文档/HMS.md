# HMS 角色调度设计

HMS（`herdr-mattpocock-skills`）按工作性质选择 agent、模型和思考等级，安排执行会话并把结果送回发起者。模型自己的开发计划和 Matt 技能都能使用 HMS。工作内容、依赖、并行度、上下文要求和完成标准沿用当前工作流。

设计与评审修订由用户于 2026-11-18 在会话 `01a1ee2f-4af2-7ac2-ae37-9902a7231a7f` 确认，以 Q25 确认稿及随后对评审 Q1–Q9 的答复为准。

## 启用与配置

用户主动引用 HMS 后，默认简单模式。本轮要求“多 agent”“团队”或使用 Matt wayfinder 即进团队。中途升级时创建本轮团队成员表，沿用本轮临时配置，已有前端先交接。单独调用 Matt wayfinder 仍按 Matt 执行。

| 模式 | 主面板和执行面板 | 开工方式 |
| --- | --- | --- |
| 简单 | 引用 HMS 的当前 agent 沿用自己的工具和模型，和用户对话、做后端、调度其他工作。第一次出现前端任务时才开第二个开发面板。 | 直接执行。用户可以当场说“前端用 Claude Code 开发”。 |
| 团队 | 当前主面板担任秘书。全队共用一个显式 PM，前后端按票开显式面板。 | 开发派工前，秘书向用户展示本轮全部身份，包括可能按需调用的匿名身份。表中写明工具、计划使用的模型和思考等级，相同配置可合为一行并标数量。用户确认整表后，PM 开始派工。 |

HMS 和 `herdr-setup` 在仓库的 `skills/` 下平级，共用安装器。常见 CLI 的[适配模板](../../skills/herdr-setup/templates/routing.json)归 setup 管理，Gemini 使用 `agy`，DSH 使用 `dst`。模板的模型留空，默认思考等级为 `high`。项目首次使用或尚未激活时，setup 展示“身份、项目 CLI、模型、默认思考等级”表。用户填写需要的身份后，setup 生成激活的 `.agents/herdr/routing.json`，只收录选用的 CLI。主会话沿用自身设置。

HMS 日常读取项目激活配置。临时换 CLI 时沿用项目为该 CLI 填过的唯一型号。有多个或没有具体型号时问一次，用户可明确选 `default`。团队中途新增身份或更换配置时只补确认变化项，用户亲自点名即为确认。工具各入口的选型方式归 [setup 参数参考](../../skills/herdr-setup/references/cli-options.md)。

## 身份与委托

| 身份 | 会话与职责 |
| --- | --- |
| 秘书 `secretary` | 主面板。与用户沟通，承担 plan、grilling、建 map 和团队模式的开工确认。 |
| PM `pm` | 团队模式的显式面板。按票调度前后端，在用户授权范围内审批或合并，汇总自己发起的任务并回报秘书。 |
| 逐票 `wayfinder` | 用户明确要求串行推进 map 时，每票开一个新的显式会话。票的类型、决策内容和处理步骤由 Matt 决定。 |
| 前端 `frontend` | 前端代码由对应的前端 agent 编写。简单模式使用第二个开发面板，团队模式按票派人。 |
| 后端 `backend` | 后端代码在简单模式由主面板编写，在团队模式由本票的后端 agent 编写。 |
| 搜索 `searcher` | 匿名，匹配搜索、代码探索和 research。使用 Matt 时，调查内容与产物由相应技能决定。 |
| 审查 `reviewer` | 匿名，匹配评审。评审视角、所需的独立上下文及返回内容由当前工作流决定。 |
| 方案设计 `designer` | 按需匿名。为工作流要求的独立方案选择模型，方案数量和比较方式由该工作流决定。 |
| 合并 `merger` | 普通已授权合并可由 PM 自行执行。工作流要求独立合并者时，PM 调独立的 merger，按该流程要求的会话形态执行。 |

匿名身份仅在同工具同模型、宿主能落实等级、工作目录和所需上下文时走原生 subagent。换工具、换型号或宿主能力不足时按原流程用相应的无头 CLI。

## 按票执行

团队模式由 PM 分票。没有正式工单时，PM 可以按当前开发计划中的任务派组。

| 本票的工作 | PM 派出的执行者 | 主实现者 |
| --- | --- | --- |
| 只有前端 | 前端 | 前端 |
| 只有后端 | 后端 | 后端 |
| 跨前后端 | 同一票的一名前端和一名后端 | 该票的后端 |

例如，10 张跨端票共用一个 PM，每票各有一名前端和一名后端。可同时推进哪些票由依赖决定。Matt 的 `implement-spec` 要求每票使用新的实现者上下文、独立的 worktree 和分支。fresh 实现者按项目对应端的型号与等级开新面板。跨端在同一票级 worktree 依序交接，整体交独立 merger。纯前端票由前端主责。简单模式直接遇到 fresh 要求时也由主 agent 调度显式实现面板。

秘书使用 Matt 的 `wayfinder` 时，通过 searcher 派发 research，建完 map 即停。用户明确要求串行推进后才逐票开 wayfinder，发送技能、map 和当前票的引用。HITL 由用户在票面板里回答。进入开发时才确认角色并开 PM。

## 面板、回报和记录

- `SKILL.md` 提供 HMS 的模式选择、命令和团队登记约定。派工正文附本轮 context、回报命令和该文件的路径。`herdr-setup` 只写项目路由配置。适配 Matt 的身份由对应技能确定工作内容。
- 每个需要派工的 agent 都可以调用 HMS。脚本把配置传给实际的 agent 工具，用 Herdr 创建显式面板，核对目标会话，并随任务传递任务标识、HMS 入口和发起者的回报地址。显式派工与回报通过 `herdr agent prompt` 直接发送正文。定位依据是已核对的面板与会话，回报沿派工时给定的地址返回。
- 显式回报核对任务标识，直回发起者。发起者等待审批时最多等一分钟，超时保留结果及面板供重发。原生 subagent 由宿主接收返回值，无头 CLI 输出直返。
- PM 判断成员工作完成，等其回合结束即关闭面板。秘书关闭 PM 及逐票 wayfinder，简单模式主 agent 关闭前端。借用面板保留，明确移交管理后由负责人收尾。
- 仅 HMS 团队模式写 `.agents/herdr/<时间戳>-<recap标题>.md`，每轮一表。登记本轮秘书、显式成员、匿名 CLI 和原生 subagent，包含失败调用。中途转团队从升级时登记。四列为会话 ID、Agent 工具、实际模型、思考等级。原生 ID 取不到写“未取得”，实际模型或等级查不到写“未核实”。工作流产物按原规则保存。
